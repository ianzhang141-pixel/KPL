# 为什么王者荣耀不能照抄 LOL 那一套

> 这份文档是整个仓库最该先读的一份。
> 如果只记住一句话：**LOL 项目能继承的是纪律，不是代码。**

---

## 一、最根本的那条差异

| | LOL（Riot 项目） | 王者荣耀（本项目） |
| --- | --- | --- |
| 数据来源 | Riot 官方 API | **没有公开的对局数据接口** |
| 一场比赛怎么拿到 | 两次 HTTPS 请求 | 看录像，一帧一帧把数字读出来 |
| 拿到的是什么 | 结构化 JSON，字段齐全 | 一堆图片 |
| 数字的性质 | **事实** | **推断** |
| 十个人的位置 | Timeline 里直接有 | 得从小地图上认出来 |
| 一场的成本 | 约 2 秒 | 人工标注约 20~40 分钟 |

> ⚠️ **需要你确认的一点：** 我没有办法在这里联网核实腾讯目前是否开放了某种
> 对局数据接口（王者营地、开放平台等）。上表按「没有」来写。
> 如果你知道有，**请立刻告诉我** —— 那会让下面一半的设计变得没必要，
> 这个项目的形态会完全不同。

这一条差异不是「麻烦一点」，它改变了系统的形状。
LOL 那边的难点在建模（V(s)、Q(s,a)），数据是白给的；
这边的难点**从建模往前挪了一整段**，卡在「怎么可靠地拿到数据」。

---

## 二、由此产生的三个新问题（LOL 完全不需要考虑）

### 1. 每个数字都得说清楚「你怎么知道的」

LOL 的 `totalGold = 8421` 是 Riot 给的，没有第二种可能。
这边的 `8421` 是从记分板上认出来的，可能是 `3421`，可能是 `8471`。

如果照抄 LOL 的结构只存一个 `8421`，下游所有人 —— 包括几个月后接手的 AI ——
都会把它当事实。等模型训出来发现不对劲，**已经没办法回头区分**
「模型的问题」还是「输入里本来就有三成是错的」。

所以本项目里每个可观测字段都是三元组：值 + 来源 + 置信度。
详见 `kplab/schema.py`。这是本项目相对 LOL 增加的最主要的结构。

### 2. 「没读到」和「是 0」必须分开

这是上一条的推论，但值得单独说，因为它是最容易犯的错。

`redGold` 这一帧没认出来，如果写成 0，经济差立刻变成 +12000，
一个巨大的假优势，而且**看起来完全正常**，任何一步都不会报错。

本项目里没读到就是 `None`，参与计算时结果也是 `None`
（`schema.derive()` 只要有一个输入未知，输出就是未知）。
宁可让报表上出现一堆「—」，也不要一个自信的假数字。

### 3. 数据质量本身要被测量

LOL 只需要问「这个字段有没有」。
这边还要问「有的那些，有多少是对的」。

所以多了 `evaluate.py`：拿人工标注当标尺去量自动识别的准确率。
**没有人工标注就没有标尺**，这也是为什么人工标注排在 OCR 前面。

## 三、从 LOL 项目直接继承的教训

这些是那边已经踩过、这边不用再踩的坑。

### ① 原始数据必须落档，而且从第一天就压缩

LOL 项目最严重的问题是「原始 Timeline JSON 从不落盘」：
解析完就丢，每改一次 State 定义就要把所有比赛重新下载一遍。

这边的原始数据是「观测」（`observations.jsonl.gz`），只追加不改写。
改 State 定义只要重跑 `kplab state`，不用重新看一遍录像 ——
考虑到这边重看一遍是几十分钟人工，这条比 LOL 那边还要重要。

压缩也是从第一天就做。LOL 的路线图里算过一笔账：不压缩存 5 万场是 98GB，
MacBook Air 装不下，于是「改成 gzip」变成了必须回头返工的一项。
这边不给自己留这个坑。

### ② 语义不同的东西不许合并进同一个计数器

LOL 项目有一个明确的 bug：

```python
elif mt in {"BARON_NASHOR", "RIFTHERALD", "HORDE"}: cumulative[kt]["barons"] += 1
```

先锋和虚空幼虫被算进了大龙。开局吃 6 个幼虫，界面显示「大龙 6 条」。
**这个 bug 不会报错，只会安静地把训练数据弄坏。**

王者荣耀更容易犯这个错，因为中立资源更多、名字更像：

| 必须分开的 | 为什么 |
| --- | --- |
| 暴君 / 黑暗暴君 | 同一个位置的两个阶段，收益完全不同 |
| 主宰 / 风暴龙王 / 先知主宰 | 同一个位置的不同阶段，价值差一个数量级 |
| 暴君 / 主宰 | 两条河道的两种东西，一个给经济一个给推进 |

`kplab/state.py` 的 `_apply_event()` 里，这五种各占一行独立分支，
**故意写得啰嗦，不合并**。

### ③ 不能泄漏未来信息

规矩和 LOL 一样：t 时刻的 State 只能含 t 时刻及之前的信息。

但这边多一个 LOL 没有的陷阱：**回头修正**。
第 5 帧读出经济 3000、第 6 帧读出 2000，总经济只增不减，必有一错。
「用第 6 帧修第 5 帧」很自然，曲线也更好看 —— 但那是拿未来改过去。
一旦这么做，用它训出来的模型在真实对局里（那时没有第 6 帧）根本没法复现。

本项目只做前向处理：第 6 帧的坏读数被丢弃并沿用第 5 帧的值，
**第 5 帧写下之后永不改动**。

### ④ Q(s,a) 必须是因果的，不是拟合出来的

LOL 项目里 GPT 那版把 action 当普通特征去拟合 `P(赢 | state, action)`，
学到的是「回城和赢相关」而不是「回城导致赢」—— 因为优势方才有余裕回城。

这边一行相关的代码都还没写，但坑先标在这里，免得以后有人图快踩进去。
**本仓库里不存在任何胜率模型或 Q 值实现，一个都没有。**

### ⑤ 诚实地写验证程度

LOL 项目的交接文档里写着「用真实 Riot 数据跑通：❌ 从未验证」。
那句话的价值超过它旁边所有打勾的条目。

本项目同样：所有「已完成」都只表示**用合成数据跑通了代码路径**。
一场真实的王者荣耀比赛都还没有进过这个系统。

## 四、这边独有的、LOL 没有的困难

诚实地列出来，不粉饰。

### 1. 小地图上的十个点，目前认不出来

记分板上的经济和比分是文字，OCR 能读。
小地图上的英雄是**彩色圆形头像，不是文字**，OCR 读不了，
需要模板匹配 / 颜色分割那类图像处理。**本版本没有实现。**

后果和 LOL 路线图里说的完全一样：

> 外部模型不知道敌方打野在哪，而这正是「入侵值不值」所必需的。

所以位置目前只能人工在标注页上点。这是本项目最大的技术缺口。

### 2. 转播画面不等于游戏状态

录像里看到的是导播选择让你看到的东西。
镜头在下路时，上路发生了什么就是不知道 —— 这不是识别不准，是**信息本身不存在**。

Riot 的 Timeline 是从服务器导出的，没有这个问题。
这意味着即使 OCR 做到 100% 准确，这边的 State 也永远比 LOL 那边稀疏。
建模时必须把「这一帧没观测到」当成一等公民，不能假设满值。

### 3. 人工标注的成本是硬约束

一场比赛人工标 40 帧、每帧十几个字段，大约 20~40 分钟。
LOL 那边采一万场是 6.7 小时挂机；这边人工标一万场是不可能的。

**这决定了整个项目的规模上限。** 路线图里的数字必须按这个来算，
不能照抄 LOL 那张「几万场」的表。

---

## 五、一句话总结

LOL 项目的价值不在它的代码，在它写下来的那些**教训**：
原始数据要留、语义不能混、未来不能泄漏、相关不是因果、验证程度不许夸大。

这五条在王者荣耀这边一条不少地适用，而且因为数据是推断出来的而不是拿到的，
每一条的**后果都更严重**。
